agent-sandbox-kit

Agent 沙箱操作手冊

讓 Claude Code 和 Codex 在隔離容器裡全權限執行、不問授權，並可用 git worktree 平行開多個。 容器就是邊界，所以兩個 agent 都以 bypass 模式跑。

18邊界檢查全數通過
9設定檔案
3shell script
2agent（Claude／Codex）

只用於你自己信任的 repo

bypass 模式下，惡意專案可以讀走容器內 ~/.claude、~/.codex 的登入憑證。 這是 Anthropic 官方明列的限制。不可信的第三方程式碼請用 VM 或 cloud session。

前置作業（每台機器一次）

  1. 主機確認 git 版本 ≥ 2.48

    worktree 的相對路徑需要這個版本，否則主機端無法操作容器建出來的 worktree。

    主機的終端機
    brew install git && git --version
git version 2.50.1 (Apple Git-155)

  2. 主機把 kit 複製到你的專案

    kit 不會碰你專案根目錄的 AGENTS.md——沙箱規則放在 .devcontainer/sandbox-rules.md。接著依 README 調整 devcontainer.json 裡標了「專案自訂」的幾個地方。

    主機的終端機
    cd ~/Project/<project>
KIT=~/Project/agent-sandbox-kit
cp -r $KIT/.devcontainer $KIT/scripts $KIT/prompts .
chmod +x scripts/* .devcontainer/*.sh

  3. 主機決定 skills 從哪裡來

    建議用專案自己的一份——每個專案可以有不同的 skills，例如魔改過的 superpowers。`devcontainer.json` 裡有兩條註解掉的 mount，二選一打開。

    (a) 專案自己的，例如放在 .agent/skills/：

    .devcontainer/devcontainer.json · mounts
    // 掛給容器讀
"source=${localWorkspaceFolder}/.agent/skills,target=/opt/agent-skills,type=bind,readonly",

// 再把來源路徑本身蓋成唯讀，否則 agent 可以從 workspace 改掉自己的 skills。
// 刻意只蓋 skills 這一層——.agent/ 其餘部分必須可寫。
"source=${localWorkspaceFolder}/.agent/skills,target=${containerWorkspaceFolder}/.agent/skills,type=bind,readonly",

    (b) 機器共用的（所有專案同一份）：

    主機的終端機
    mkdir -p ~/.agent-skills
ln -sfn ~/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0 \
        ~/.agent-skills/superpowers
    .devcontainer/devcontainer.json · mounts
    "source=${localEnv:HOME}/.agent-skills/superpowers,target=/opt/agent-skills,type=bind,readonly",

    兩種目錄結構都支援，post-create.sh 會自動判斷：plugin 形式 （底下有 .claude-plugin/，例如 superpowers 的 fork）交給 cc 的 --plugin-dir；純 skills 目錄（底下直接是 <skill-name>/SKILL.md）則逐個 symlink 到兩個 agent 的探索路徑。

    容器內 · 起容器時的輸出與接線結果
    [post-create] skills：接上 2 個（來源 /opt/agent-skills）

ls -l ~/.agents/skills/          # Codex 的探索路徑
my-review -> /opt/agent-skills/my-review
my-tdd    -> /opt/agent-skills/my-tdd

ls -l $CLAUDE_CONFIG_DIR/skills/  # Claude 的 user-level skills
my-review -> /opt/agent-skills/my-review
my-tdd    -> /opt/agent-skills/my-tdd

    為什麼只蓋 .agent/skills 而不是整個 .agent/

    .agent/ 底下還有兩樣必須可寫的東西：agent 留給你的 .agent/QUESTIONS.md，以及 agent-wt 產生的 prompt.txt 與 run.sh。整個目錄掛唯讀的話這些都會失敗。

    容器內 · 實測
    echo x >> .agent/skills/my-tdd/SKILL.md
bash: .agent/skills/my-tdd/SKILL.md: Read-only file system

echo "問題" > .agent/QUESTIONS.md
✓ 寫得進去

不需要 bootstrap。 早期版本要求先在主機建一個拋棄式 worktree 來升級 .git/config，那是因為當時把 .git/config 掛成唯讀。現在已改用 core.hooksPath 檢查取代，這個步驟整個取消了。

每次要用

每一步都標了在哪裡執行： 主機是你的 Mac， 容器是沙箱裡面。指令都含 cd， 可以直接複製貼上，不必管上一步停在哪。

  1. 主機起容器

    背景先跑起來。第一次要 build（裝 apt 套件、Node、兩個 agent，數分鐘）， 之後每次只要幾秒。容器會一直在背景執行直到你手動停掉。

    主機的終端機
    cd ~/Project/<project>
npx @devcontainers/cli up --workspace-folder .

    看到最後這兩行代表成功。防火牆那行沒出現就是沒起來，不要繼續。

    輸出（節錄）
    [firewall] OK：出站已限制在白名單內（19 個網域 + GitHub IP 段）
{"outcome":"success", ... "remoteWorkspaceFolder":"/workspaces/<project>"}

  2. 主機進到容器裡

    這行會把你丟進容器的 shell。從這裡開始，你打的每個指令都在容器內執行。 要離開就打 exit（容器不會停，下次再 exec 進來就好）。

    主機的終端機
    cd ~/Project/<project>
npx @devcontainers/cli exec --workspace-folder . bash

    提示字元變成 vscode ➜ /workspaces/<project> $，代表你在容器裡了。

  3. 容器登入 Claude 和 Codex

    什麼時候要做：第一次進這個容器時，以及每次 rebuild container 之後。 平常停掉再開不用重登。

    為什麼：容器裡的 Claude 和 Codex 是全新安裝的，沒有你主機上的登入狀態 （主機的憑證刻意不掛進來——那正是沙箱要隔離的東西）。登入後 token 會存在一個 named volume 裡，所以容器重啟還在。

    容器內
    claude

# 授權完會自動回到終端機。登入成功後打 /exit 離開，回到 shell

    瀏覽器授權完，終端機卻沒反應？

    授權後瀏覽器會停在一個顯示一串代碼的頁面。把那串代碼複製、 貼回終端機的提示處按 Enter 就完成了。這是因為容器的 port forwarding 沒把 localhost 的回呼接回來，不是登入失敗。

  4. 容器確認沙箱真的關緊了

    每次進容器都要跑，不是只跑第一次——單檔唯讀 mount 會靜默脫鉤 （見下方「已知的洞」）。全 PASS 才繼續；有 FAIL 就照那一節的指令重建容器。

  5. 容器啟動 agent

    在容器的終端機打 cc 就會開起 Claude，cx 開 Codex。 之後就是平常用 agent 的樣子，差別只在它跑在沙箱裡、不會問你授權。

    容器內

    為什麼不直接打 claude：cc 是一層薄包裝， 幫你補上三樣東西——bypass 旗標、skills 的載入路徑、把沙箱規則注入系統提示。 直接打 claude 這些都不會有，它還是會一直問你授權。

    它們也會先檢查防火牆。萬一防火牆沒起來，cc 會拒絕啟動而不是讓 agent 在沒有網路限制的狀態下全權限執行：

  6. 主機用完之後

    容器不會自己停。要停掉的話回主機下這行；下次再 up 就好，不用重 build。

    主機的終端機

容器平行開多個 agent

沒有 worktree 的話，agent 和你共用同一個 checkout——它一切分支，你編輯器裡的檔案就整批被換掉。 agent-wt new 一次處理四件事：建 worktree 與分支、裝依賴、配一個不重複的 PORT、在 tmux 開視窗。

容器內
cd /workspaces/<project>
agent-wt new feat-a claude "把動作總覽的欄位改成三欄"
added 162 packages in 3s
agent-wt: worktree=/workspaces/<project>/.worktrees/feat-a 分支=agent/feat-a PORT=3120
agent-wt: [claude] 已在 tmux agents:feat-a 啟動 → tmux attach -t agents

cat .worktrees/feat-a/.git
gitdir: ../../.git/worktrees/feat-a   # 相對路徑，主機端才操作得到

agent-wt new feat-b codex @docs/some-prompt.md
tmux attach -t agents   # 切視窗：Ctrl-b n / Ctrl-b w

dev server 要用 .agent.env 裡的 $PORT： npm run dev -- --host 0.0.0.0 --port $PORT

主機收成

沒有 agent-wt diff 或 agent-wt rm——那些本來就各是一行原生 git，包起來不會更短。

在容器裡也做得到，但通常你會在主機上 review 和 merge——因為 worktree 用的是相對路徑， 兩邊都操作得到（路徑前綴不同也沒關係）。

放 agent 進去之前先 push

專案目錄在容器內可寫（agent 要能改程式碼），.git 也在裡面。 沙箱規則禁止它砍歷史，但那是文字約束不是機制。 沒 push 的 commit 被砍掉就是沒了；先 push，最壞情況只是重新 clone。

已知的洞：單檔唯讀 mount 會靜默脫鉤

工具改檔案常用「寫 .lock 再 rename」，換的是 inode；主機那側一旦換掉檔案， 容器裡的 mount 就脫鉤、檔案變回可寫，沒有任何錯誤訊息。

目錄的 mount 沒這問題——這正是沙箱規則放在 .devcontainer/sandbox-rules.md 而不是根目錄單檔的原因之一。 會受影響的只有你自己打開的那幾條單檔 mount（AGENTS.md、.mcp.json）： 在主機上編輯過就會脫鉤。開發這份設定時實測到，一次就中：

容器內 · 主機剛編輯過某個單檔 mount 的來源之後
verify-sandbox
  FAIL  .mcp.json 不可寫  → <rc=0>
PASS=17 FAIL=1
有項目未通過，請先修好再放 agent 進來。

修法是重建容器：

主機的終端機
docker rm -f $(docker ps -aq --filter label=devcontainer.local_folder=$PWD)
npx @devcontainers/cli up --workspace-folder .
PASS=18 FAIL=0

緊急關閉防火牆：sudo 已收斂，容器內辦不到。從主機下 docker exec -it -u root <容器> bash。

踩過的坑

建這套東西時撞到的問題與最後的解法。多數不是設定寫錯，是主機與容器的環境差異在某個沒預期的地方冒出來。

一、為什麼要掛整個 repo，而不是只掛 worktree

直覺上「agent 只該看到它那個 worktree」比較安全，但那樣做 git 完全無法運作，原因有兩層。

第一層 worktree 目錄裡的 .git 不是目錄，是一行指路文字，指向主 repo 的 .git/worktrees/<name>。只掛 worktree 的話這個目標不存在。
第二層 worktree 沒有自己的 object database。 所有 commit、tree、blob 都存在 主 repo 的 .git/objects/。就算想辦法把路徑接通，物件根本不在那裡—— 這不是路徑問題，是 worktree 的設計就是共用主 repo 的物件庫。
結論 掛整個 repo 根目錄不是偷懶，是唯一可行的做法。代價是 .git 可寫、 agent 有能力砍歷史，所以才有「放 agent 進去之前先 push」這條規則。

二、worktree 的連結必須是相對路徑

主機看到的是 ~/Project/<project>，容器看到的是 /workspaces/<project>。連結寫絕對路徑，就只有建立它的那一邊能用。

絕對 vs 相對
gitdir: /workspaces/<project>/.git/worktrees/feat-a  # 主機打不開
gitdir: ../../.git/worktrees/feat-a                      # 兩邊都通

agent-wt 跑在容器內，所以不加 --relative-paths 時斷掉的是主機那邊。 更麻煩的是主機的 git gc 會順便 worktree prune，看到指不到的路徑就把註冊清掉， 反過來也弄壞容器那側。

症狀加了 --relative-paths 卻還是絕對路徑，只印一行 WARN
原因 1 偵測條件 grep 的是字面 --relative-paths，但 git 的 help 印的是 --[no-]relative-paths——那個子字串在任何版本都不存在
原因 2 腳本開頭有 set -o pipefail，而 git worktree add -h 的離開碼是 129（usage），pipeline 因此永遠回傳非零，條件永遠成立
解法 不用 pipeline，改成 case "$(git worktree add -h 2>&1 || true)" in *relative-paths*)
教訓 兩個 bug 疊在一起，各自都足以讓功能失效——而失效時只有一行 WARN，很容易忽略

三、node_modules 在 macOS 裝、拿到 Linux 容器裡會炸

專案目錄是 bind mount，node_modules 預設也跟著進容器。但主機是 macOS（darwin-arm64），容器是 Linux（linux-arm64），原生 binary 不相容。

容器內 · npm test
Cannot find module '@rolldown/binding-linux-arm64-gnu'
Require stack:
- /workspaces/<project>/node_modules/rolldown/dist/shared/binding-….mjs
解法 node_modules 改用 named volume 疊在 bind mount 上，容器有自己的一份， 由 post-create.sh 跑 npm ci 填充。主機那份完全不受影響，兩邊可同時跑
順帶 named volume 預設 root 擁有，要先 chown——而這必須排在 post-create 收斂 sudo 之前，否則就沒權限了
副作用升級依賴後要 rebuild container，或在容器內自己再 npm ci 一次

四、其餘的坑

症狀原因解法
worktree add 失敗：
could not write config file .git/config: Resource busy		 首次建相對路徑 worktree 要寫 core.repositoryformatversion=1 與 extensions.relativeworktrees，但 .git/config 當時掛成唯讀。 錯誤是 EBUSY（rename 蓋不過掛載點），不是權限錯誤 拿掉那個唯讀 mount。它本來也留不住（見下一列），而它擋掉的威脅 （core.hooksPath）改由 verify-sandbox 直接檢查
唯讀保護沒有任何錯誤訊息就消失 單一檔案的 bind mount，只要主機那側用「寫 .lock 再 rename」換掉檔案 （git 與多數編輯器都這樣做），mount 就脫鉤。目錄的 mount 沒這問題 只掛目錄；剩下的單檔靠 verify-sandbox 每次偵測，FAIL 就重建容器
agent 建好 worktree 卻沒啟動，tmux 回 command too long 啟動指令把整份 AGENTS.md 用 printf %q 內嵌命令列，外層再包一次。 中文每個字會展開成多個八進位跳脫，長度爆增 產生一支 runner 腳本，內容在腳本裡才展開，tmux 只拿到一個路徑
sudo 收斂寫在 Dockerfile 卻沒效果 devcontainer features 疊在 image 之上、以 root 執行， common-utils 之類會把 NOPASSWD:ALL 寫回來 收斂移到 post-create.sh 的最後一步（features 跑完之後）
收斂了 sudo，agent 仍能改防火牆 sudoers 裡命令不寫參數 = 允許任意參數，agent 可以指向自己寫的全放行清單 重新執行防火牆腳本 把參數釘死：NOPASSWD: /usr/local/share/init-firewall.sh "" （"" 表示只允許不帶參數）
agent 無法 commit：Please tell me who you are VS Code 的擴充會自動複製主機 .gitconfig，CLI 不會。 用 Antigravity 只能走 CLI，所以一定會撞到 post-create.sh 設 user.name / user.email
防火牆啟動時 WARN 無法解析 statsig.anthropic.com 該網域解析不到 從白名單移除，少一行噪音

一個測試方法上的教訓

查「唯讀 mount 會不會擋住 worktree add」時，先在容器外用 chmod 444 .git/config 模擬——結果 git 照樣寫成功，差點得出錯誤結論。

原因是 git 不原地改檔案：它寫一個 .lock 再 rename() 蓋過去， 而 rename() 檢查的是目錄權限，不是檔案權限。 唯讀 bind mount 是掛載層的限制，行為完全不同。

mount 的語意只能在真容器裡驗，權限位元模擬不出來。

官方有而本專案刻意不要的

官方的做法本專案理由
Reopen in Container 為主要用法只用 CLI 擴充套件會注入 IPC socket、轉發 SSH agent 與 GPG，容器內可反向在主機執行指令。Trail of Bits 的結論是不建議用於不可信程式碼
zsh + powerlevel10k + git-delta不裝 agent 不需要好看的 shell，image 可以小一點
CLAUDE_CODE_VERSION=latest ＋ 自動更新釘死版本 Anthropic 自己也建議：要可重現的 build 就用 npm i -g …@X.Y.Z 而非 feature
eslint / prettier / gitlens 擴充只留兩個 agent 的擴充 編輯器在主機，容器內的擴充用不到

三個容易誤解的設計

看起來奇怪的地方原因
規則不放在專案根目錄 規則放在專案根目錄有兩個問題：會蓋掉專案自己的 AGENTS.md，而且主機上的 session 也會讀到「你在容器內、權限全開」——在主機上是錯的。所以規則放 .devcontainer/sandbox-rules.md：Claude 由 cc 以 --append-system-prompt 注入，Codex 由 post-create 複製到 $CODEX_HOME/AGENTS.md（全域層，專案自己的 AGENTS.md 優先權更高）。兩邊都不碰你的檔案
cc／cx 是執行檔不是 alias agent-wt 產生的 runner 是非互動 bash，不會 source /etc/bash.bashrc，函式放那裡用不到；而且烤進 image 後 agent 改不掉
sudo 收斂在 post-create.sh 而非 Dockerfile devcontainer features 疊在 image 之上、以 root 執行，會把 NOPASSWD:ALL 寫回來，抵銷 Dockerfile 裡做的任何收斂。所以收斂必須是最後一步
